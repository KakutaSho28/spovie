## 1. Current state (already implemented — Phase 1 MVP)

Monorepo layout:

```
docker-compose.yml, docker/{php,nginx,mysql}
backend-overlay/   # Laravel app code, copied into backend/ by scripts/setup-backend.sh
frontend/          # React 18 + TS + Vite
docs/              # design docs (Markdown, mirrored to Notion)
```

- Backend: Laravel 10 / PHP 8.2 / Sanctum (Bearer token). Controllers: Auth, Video, VideoUpload, Annotation, Share, Clip. Job: `ProcessClipJob` (FFmpeg `-c copy`, Laravel Queue `database` driver). Models: User, Video (type = youtube|upload), Annotation, ShareLink, Clip.
- Frontend: Login, Register, Videos, VideoNew (YouTube URL / mp4 upload tabs), Annotations, Annotate (Fabric.js canvas over YouTube IFrame or HTML5 video), ClipStatus, Share. Zustand auth store, Axios client with token interceptor.
- Annotation coordinates are stored normalized (0–1) so they can be re-rendered at any screen size.
- Copyright policy (do not change): YouTube videos support annotation + share links only (no clipping / no saving video data). Only uploaded videos can be clipped and downloaded.

Local setup caveat: `backend/` is generated by `scripts/setup-backend.sh` (composer create-project + overlay). Keep that flow working, but see WP0 about making it less fragile.

## 2. Working rules (read first)

1. **Create `CLAUDE.md` at the repo root first** (WP0) and keep it updated. Include: stack, directory map, how to run (docker compose), how to run tests/build, coding rules below, and the copyright policy above.
2. Use **Plan Mode** at the start of each work package: write a short plan, then implement.
3. Git workflow: one branch per work package (`feature/wp3-teams` etc.), small conventional commits (`feat:`, `fix:`, `docs:`, `chore:`), merge into `develop`, and `develop` → `main` only after verification. Pushing to `main` triggers the production deploy (after WP3).
4. **Verify before declaring done.** After each work package run: `php artisan test`, `php artisan route:list` (no conflicts), `npm run build` (TypeScript strict must pass), and exercise the feature against the running stack (curl / Playwright). Report what you actually ran.
5. Never commit secrets. `.env` stays git-ignored; add every new variable to `.env.example`. Never invent credentials.
6. Do not run anything that needs the human's dashboard login (Railway / Vercel / Pusher / AWS consoles). Prepare config files and output an exact **"Manual steps for the human"** checklist instead. If a CLI (`railway`, `vercel`) is already logged in, you may use it, but say so.
7. Frontend: TypeScript strict, no `any`. Backend: FormRequest for validation, Resource for responses, authorization checks in controllers/policies, response envelope `{ "data": ... }` / `{ "message": ... }`.
8. UI copy is Japanese. Code, commit messages, docs headings in English or Japanese consistently with the existing files.
9. Keep scope tight. If something is not listed here, don't build it. Prefer finishing a smaller version of each package over leaving anything half-done.

## 3. Work packages (in priority order)

### WP0 — Repo hygiene and test harness (≈1h)
- Create `CLAUDE.md`.
- Make backend bootstrapping reproducible: either commit a full Laravel 10 `backend/` (preferred, removes the overlay indirection and is required for Railway to build from the repo), or keep overlay but document it. **Recommended: commit the full `backend/` and delete `backend-overlay/` + `setup-backend.sh`, updating docs.** Ensure `backend/.env`, `vendor/`, `storage` contents are ignored.
- Add PHPUnit feature-test scaffolding (sqlite in-memory) and a minimal GitHub Actions workflow: backend tests + frontend build on every PR.

### WP1 — Correctness fixes in existing code (≈2h)
Fix these known gaps, with tests:
1. **Annotate page loads the video by scanning the paginated `GET /videos` list** → add `GET /api/videos/{video}` (owner/team-member only) and use it. The scan breaks past 20 videos.
2. **Share links don't support uploaded videos** (`ShareController@show` returns only `youtube_video_id`). Return `video.type` and `video.file_url`; make `Share.tsx` render HTML5 video for uploads (with `useHtml5VideoLoop`) and YouTube for youtube.
3. **Verify canvas normalization round-trip.** `normalizeObject/denormalizeObject` in `AnnotationCanvas.tsx` use a scale heuristic that may break for pen paths and groups. Write a Playwright check: draw pen + arrow + text at 1280px wide, save, reopen at 640px wide, and confirm shapes land at the same relative positions. Fix the math if not (e.g. normalize with explicit width/height ratios and re-apply on load).
4. Add a `Policy`/guard so non-owners get 403 consistently on videos, annotations, clips, share links.
5. `ClipController@download` is intentionally unauthenticated (shareable via LINE); make the clip id non-guessable by adding a `download_token` (random 40 chars) column and using `/api/clips/{clip}/download/{token}`. Update `ClipResource.download_url`.

### WP2 — Storage abstraction + S3-compatible storage (≈2h)
Production hosts have ephemeral disks, so uploaded videos and clips must live in object storage.
- Add `league/flysystem-aws-s3-v3`. Configure the `s3` disk to support **any S3-compatible endpoint** (AWS S3 or Cloudflare R2): `AWS_ENDPOINT`, `AWS_USE_PATH_STYLE_ENDPOINT`, `AWS_URL`.
- Replace every hard-coded `Storage::disk('public')` with `Storage::disk(config('filesystems.default'))` (VideoUploadController, ProcessClipJob, ClipController, VideoResource, ShareController).
- `ProcessClipJob` with S3: download source to a temp file, run FFmpeg locally, upload the result, delete temp files (also on failure).
- Video playback URLs for private buckets: use temporary signed URLs (`temporaryUrl`, ~1h) when the disk is not `public`.
- Local dev keeps `FILESYSTEM_DISK=public`.
- Reduce the production upload limit to **200MB** (configurable via env) and document why (proxy timeouts). Stretch goal only if time remains: direct-to-S3 presigned upload.

### WP3 — Deploy to production early (≈2–3h) — do this before the big features
Goal: a public URL as early as possible so the "3" level is secured, then every later package ships continuously.
- **Backend → Railway** (Docker deploy from `backend/`):
  - Add a production `Dockerfile` (php-fpm + nginx in one image via supervisord, includes `ffmpeg`, runs `php artisan migrate --force` and `config:cache`/`route:cache` on start, listens on `$PORT`).
  - Services: `web` (API), `worker` (same image, start command `php artisan queue:work --tries=1 --timeout=600`), and a Railway **MySQL** plugin. Provide a `railway.json`/documented start commands.
  - Env: `APP_KEY`, `APP_ENV=production`, `APP_DEBUG=false`, DB vars from Railway MySQL, `QUEUE_CONNECTION=database`, `FILESYSTEM_DISK=s3`, AWS/R2 vars, `APP_FRONTEND_URL`, `SANCTUM_STATEFUL_DOMAINS`, Pusher vars (WP5).
  - CORS: restrict `config/cors.php` allowed origins to the Vercel domain(s) via env (`CORS_ALLOWED_ORIGINS`).
  - Trust proxies so Laravel generates `https` URLs.
- **Frontend → Vercel**: project root `frontend/`, `vercel.json` with SPA rewrite to `index.html`, `VITE_API_BASE_URL` pointing to the Railway API URL.
- Add a `/api/health` endpoint (DB check) for uptime verification.
- Smoke-test production with curl: register → login → create YouTube video → create annotation → create share link → open share link JSON.
- Output **"Manual steps for the human"**: exact list of dashboard actions (create Railway project/services/MySQL, set env vars, create bucket and keys, create Vercel project, connect GitHub), with every env var name and where it goes.

### WP4 — Teams (F17) (≈3h)
Tables (new migrations only):
- `teams` (id, name, owner_id FK users, invite_token unique 64, timestamps)
- `team_members` (id, team_id FK, user_id FK, role enum owner|member, joined_at, unique(team_id,user_id))
- `videos.team_id` nullable FK → teams (on delete set null)

API (all `auth:sanctum`):
| Method | URI                              | Notes                                                            |
| ------ | -------------------------------- | ---------------------------------------------------------------- |
| POST   | /api/teams                       | creator becomes owner and first member                           |
| GET    | /api/teams                       | teams the user belongs to                                        |
| GET    | /api/teams/{team}                | details + members (members only)                                 |
| DELETE | /api/teams/{team}                | owner only                                                       |
| POST   | /api/teams/join                  | body `invite_token`; idempotent                                  |
| DELETE | /api/teams/{team}/members/{user} | owner removes member; member may remove self; owner cannot leave |
| GET    | /api/teams/{team}/videos         | members only                                                     |

- `VideoController@index` returns personal videos plus videos of the user's teams (support `?team_id=` filter and `?scope=personal|all`). `POST /videos` and `/videos/upload` accept optional `team_id` (must be a team the user belongs to).
- Authorization everywhere that touches a video/annotation/clip: owner **or** member of the video's team.
- Frontend: `Teams`, `TeamNew`, `TeamDetail`, `TeamJoin` (`/teams/join/:token`; if not logged in, remember the token, go through login, then join), team filter on `Videos`, team selector on `VideoNew`, "チーム" link in `Layout`.
- Feature tests for each authorization rule (member vs non-member vs owner).

### WP5 — Comments + real-time with Pusher (F18) (≈4h) — core of the rubric's "real-time"
Comments:
- `comments` (id, annotation_id FK cascade, user_id FK cascade, body text ≤1000, timestamps)
- `GET/POST /api/annotations/{annotation}/comments`, `DELETE /api/comments/{comment}` (author only). `CommentResource` includes `user {id,name}` and `is_own`.
- `CommentThread.tsx`, expandable per card in `Annotations.tsx` and also shown on `Annotate.tsx`.

Real-time (Laravel Broadcasting + Pusher Channels):
- Backend: `composer require pusher/pusher-php-server`; `BROADCAST_DRIVER=pusher`; events `CommentCreated`, `CommentDeleted`, `AnnotationCreated` implementing `ShouldBroadcast` (queued on the worker) on **private channels**: `private-annotation.{id}` and `private-video.{id}`.
- Channel authorization in `routes/channels.php`: allowed if the user owns the video or belongs to its team.
- **Gotcha:** the API sits behind `/api` only (nginx / Railway routing). Register the auth route under the API prefix with Sanctum: `Broadcast::routes(['prefix' => 'api', 'middleware' => ['auth:sanctum']])` so the endpoint is `/api/broadcasting/auth`.
- Frontend: `laravel-echo` + `pusher-js`, singleton in `src/lib/echo.ts`, `authEndpoint` = `${API}/broadcasting/auth` with `Authorization: Bearer <token>` header; env `VITE_PUSHER_APP_KEY`, `VITE_PUSHER_APP_CLUSTER`. Subscribe in `CommentThread` (append/remove comments live, de-duplicate with the optimistic local add) and in `Annotations` page (new annotations appear live). Unsubscribe on unmount.
- Show a small connection-state indicator ("リアルタイム接続中") — useful for the demo.
- Test: broadcast events are dispatched (`Event::fake`) on create/delete; manual two-browser check documented.

### WP6 — PWA (≈3h)
- `vite-plugin-pwa` (Workbox, `registerType: 'autoUpdate'`), web app manifest (name Spovie, `display: standalone`, theme color `#ff8a3d`, background `#101513`), icons 192/512 + maskable + apple-touch-icon (generate simple original icons; do not use third-party logos).
- Caching strategy: precache the app shell; runtime `NetworkFirst` for `GET /api/*` (short timeout, ~5 min max-age); **never cache** video files, clip downloads, or `/api/broadcasting/auth`.
- Offline experience: an offline fallback page, and an "オフラインです" banner (via `navigator.onLine` + events). Previously loaded list screens should still render from cache. Be explicit in UI that YouTube playback and saving need a connection.
- Install prompt: a small "ホーム画面に追加" button using `beforeinstallprompt`.
- Verify with Lighthouse (PWA/installable checks) against the **production URL** and save the report summary into `docs/`.

- `README.md` (English or Japanese, consistent): overview, features, architecture diagram (Mermaid), tech stack, local setup, deployment, env variable table, public URL, demo account.
